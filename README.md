# Mini NPU Simulator

입력 패턴과 필터를 위치별로 곱하고 모두 더하는 **MAC(Multiply-Accumulate) 연산**으로 패턴이 십자가(Cross)인지 X인지 판정하는 Python 콘솔 프로그램입니다. 외부 라이브러리 없이 표준 라이브러리(`json`, `time`)만 사용합니다.

## 실행 방법

```bash
python main.py
```

- **실행 환경:** Python 3.8 이상 (개발 환경: Python 3.12.10, Windows)
- **data.json 위치:** `main.py`와 같은 폴더에 두고, 그 폴더에서 실행합니다.
- **모드 선택:** 실행 후 `1` 또는 `2`를 입력합니다.
  - `1` 사용자 입력 (3×3): 필터 A, B와 패턴을 한 줄에 숫자 3개씩(공백 구분) 3줄 입력
  - `2` data.json 분석: 파일의 모든 패턴을 일괄 판정하고 성능 표와 요약 출력

### 모드 1 입력 예시

```
필터 A (3줄 입력, 공백 구분)
0 1 0
1 1 1
0 1 0
필터 B (3줄 입력, 공백 구분)
1 0 1
0 1 0
1 0 1
패턴 (3줄 입력, 공백 구분)
1 0 1
0 1 0
1 0 1
```

결과: `A 점수: 1.0`, `B 점수: 5.0`, `판정: B`

## 구현 요약

### MAC 연산 (`mac`)
- 이중 `for`문으로 모든 위치 `(i, j)`를 방문하며 `pattern[i][j] * filter[i][j]`를 누적합니다.
- 합계를 `0.0`으로 시작해 결과를 항상 float로 반환합니다. NumPy 등 벡터화 라이브러리는 쓰지 않았습니다.

### 라벨 정규화 (`normalize_label`)
- 프로그램 내부에서는 표준 라벨 **Cross / X** 두 가지만 사용합니다.
- `strip().lower()`로 공백과 대소문자를 정리한 뒤 매핑합니다: `"+"`, `"cross"` → `Cross` / `"x"` → `X`
- expected 값과 필터 키 모두 같은 함수로 정규화하므로 비교 기준이 하나로 통일됩니다.
- 매핑에 없는 라벨은 `None`을 반환하고, 해당 케이스를 FAIL로 처리합니다.

### 동점 처리 정책 (`judge`)
- `abs(score_a - score_b) < 1e-9`이면 동점으로 보고 **UNDECIDED**(모드 1에서는 "판정 불가")를 반환합니다.
- 그 외에는 점수가 큰 쪽 라벨을 반환합니다.

### 입력 검증과 스키마 검증
- **모드 1:** 한 줄의 숫자 개수가 3개가 아니거나 숫자로 변환할 수 없으면 안내 문구를 출력하고 **그 줄만 다시 입력**받습니다.
- **모드 2:** 아래 문제가 있으면 프로그램을 멈추지 않고 **해당 케이스만 FAIL** 처리한 뒤 사유를 기록합니다.

| 검사 | 실패 사유 메시지 |
|---|---|
| 키가 `size_{N}_{idx}` 형식이 아님 | 키 형식 오류 |
| `size_N` 필터가 없음 | size_N 필터가 없음 |
| `input` 또는 `expected` 누락 | 스키마 오류 |
| 패턴이 N×N이 아님 | 크기 불일치 (패턴 a×b, 필터 N×N) |
| 숫자가 아닌 값 포함 | 데이터 오류 |
| expected가 알 수 없는 라벨 | 알 수 없는 expected 라벨 |

- 파일이 없거나 JSON 문법이 깨진 경우에도 안내 메시지를 출력하고 종료합니다.

### 성능 측정 (`measure_mac_ms`)
- `time.perf_counter()`로 **MAC 함수 호출 구간만** 10회 반복 측정해 1회 평균(ms)을 계산합니다. 입력, 출력, 파일 읽기 시간은 포함하지 않습니다.
- data.json에는 3×3 데이터가 없으므로, **패턴 생성기(`generate_pattern`)**로 3×3, 5×5, 13×13, 25×25 십자가를 만들어 동일한 조건으로 측정합니다. (보너스 과제: 패턴 생성기)

### 2. 실패 원인 분석

실패 원인을 **데이터·스키마 문제 / 로직 문제 / 수치 비교 문제** 세 가지로 나누어 진단했습니다.

- **데이터·스키마 문제: 해당 없음.** 모든 키가 `size_{N}_{idx}` 형식이고, 필터와 패턴 크기가 일치하며, 라벨(`"+"`, `"x"`, `"cross"`)은 정규화로 모두 표준 라벨로 변환되었습니다.
- **로직 문제: 해당 없음.** 점수 차이가 분명한 3개 케이스(size_5_2, size_13_1, size_25_2)는 모두 expected와 같은 판정으로 PASS했습니다. MAC 연산과 판정 로직은 정상입니다.
- **수치 비교 문제: 실패 3건 모두 여기에 해당합니다.**

실패한 3개 케이스는 **필터 가중치가 두 점수를 수학적으로 정확히 같게 만들도록 설계**되어 있습니다.

| 케이스 | Cross 쪽 계산 | X 쪽 계산 | 수학적 값 |
|---|---|---|---|
| size_5_1 (X 패턴) | 중앙 가중치 0.9 × 1칸 | 0.1 × 9칸 | 둘 다 0.9 |
| size_13_2 (Cross 패턴) | 0.3 × 25칸 | 중앙 가중치 7.5 × 1칸 | 둘 다 7.5 |
| size_25_1 (X 패턴) | 중앙 가중치 4.9 × 1칸 | 0.1 × 49칸 | 둘 다 4.9 |

그런데 컴퓨터는 0.1이나 0.3 같은 소수를 2진수로 정확히 표현하지 못합니다. 그래서 여러 번 더하는 과정에서 `0.8999999999999999`처럼 **1e-16 ~ 1e-15 수준의 오차**가 생깁니다.

**epsilon 정책이 없었다면?** 단순히 `>`로 비교하면 이 미세한 오차가 판정을 결정합니다.
- size_5_1: 0.9 > 0.8999…이므로 Cross로 판정 (정답 X) → 틀린 답
- size_13_2: 7.4999… < 7.5이므로 X로 판정 (정답 Cross) → 틀린 답
- size_25_1: 4.9 > 4.8999…이므로 Cross로 판정 (정답 X) → 틀린 답

FAIL 개수는 똑같이 3개이지만, 이 경우 프로그램은 **근거 없는 판정을 확신 있게 내놓습니다**. epsilon(1e-9) 정책을 적용하면 세 케이스의 점수 차이(1.11e-16, 2.66e-15, 1.78e-15)가 모두 1e-9보다 작으므로 **"판정 불가(UNDECIDED)"**로 정직하게 보고합니다.

**결론:** 3건의 FAIL은 프로그램 오류가 아니라, 두 필터가 이 패턴을 **구별하지 못한다**는 사실을 정확히 드러낸 결과입니다. 판정 정확도를 높이려면 비교 정책이 아니라 **필터 가중치 설계**를 바꿔야 합니다.

### 3. 성능 분석과 시간 복잡도

측정 환경: Windows, Python 3.12.10 / MAC 10회 반복 평균

| 크기 (N×N) | 평균 시간 (ms) | 연산 횟수 (N²) | 3×3 대비 연산 횟수 | 3×3 대비 시간 |
|---|---|---|---|---|
| 3×3 | 0.0034 | 9 | 1.0배 | 1.0배 |
| 5×5 | 0.0055 | 25 | 2.8배 | 1.6배 |
| 13×13 | 0.0267 | 169 | 18.8배 | 7.9배 |
| 25×25 | 0.0971 | 625 | 69.4배 | 28.6배 |

**O(N²)의 근거**
- **코드 구조:** `mac`은 바깥 반복문이 N번, 안쪽 반복문이 N번 돌아 곱셈과 덧셈을 정확히 **N × N = N²번** 수행합니다. 따라서 시간 복잡도는 **O(N²)**입니다.
- **측정 결과:** 크기가 충분히 큰 구간에서 이론과 측정이 거의 일치합니다.
  - 13×13 → 25×25: 연산 횟수 **3.70배**, 측정 시간 **3.64배**
- **작은 크기에서 비율이 어긋나는 이유:** 3×3과 5×5에서는 시간이 연산 횟수만큼 늘지 않습니다. 함수 호출, 반복문 준비 같은 **고정 비용**이 전체 시간에서 차지하는 비중이 크기 때문입니다. 연산 1회당 시간을 보면 3×3은 약 0.38µs이고, 13×13과 25×25는 약 0.16µs로 수렴합니다. N이 커질수록 고정 비용의 비중이 줄고 N²에 비례하는 부분이 시간을 지배합니다.
- **시사점:** N이 2배가 되면 연산량은 4배가 됩니다. 실제 AI 모델은 훨씬 큰 필터를 수천 개 사용하므로 연산량이 폭발적으로 늘어나고, 이것이 CPU의 순차 처리 대신 MAC을 병렬로 처리하는 **NPU**가 필요한 이유입니다.
